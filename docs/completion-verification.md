# 报告可读与研究完成

## 三种证据分别判断

`scripts/verification.py` 继续作为唯一运行对账器；不读取此前写下的 PASS 来批准本轮。

| 字段 | 证明范围 |
| --- | --- |
| `status` / `scope=saved_evidence_integrity` | 搜索候选逐 ID 对账、原缓存数值复算、已保存判断的输入绑定、预算和实际报告一致性。允许保留明确列出的未核验项，不代表研究目标完成。 |
| `completion.report.available` | 已有结构可读的 HTML，包括阶段结果。仅有文件不证明当前数据与报告一致。 |
| `completion.report.ready` | 当前稿通过既有报告合同、完整 HTML、全部合格图卡和数值核对；有要求时还需实际保存的自动内容审核。 |
| `completion.retrieval` | 从请求预留、请求记录和缓存重新计算关键词页数、真实翻页前沿、故障、剩余额度与核验预留。 |
| `completion.quantity` | 本轮已核验且相关的作品数，默认目标下限 20、目标区间 20–30；正文最多精选 3 条不改变结果池目标。 |
| `completion.overall_goal_met` | 非合成任务，报告可用、策略停止有证据、已发现候选全部处理完整、数量达标才为真。 |

任务处于 `report_ready` 时可以直接打开正文，历史页显示“已有报告 · 目标未全部达成”。内部过程留在运行记录，不重新塞进报告。`done` 仅用于目标已核实或明确标注的合成示例；旧数据库的 done 不自动作为新判定证据，读取时重新评估但不改数据库。

## 对账与停止

核验器从标准化搜索响应枚举有效视频 ID，核对全部候选、逐条判断与结果。播放量从原 stats/stats_bulk 缓存恢复；作者历史从原 posts 缓存按游标重建，再用相同数学规则重算，避免状态与报告同时被改后仍自洽。normal 和 lite 历史均保留支持。最终图卡集合必须恰好等于全部合格结果集合，不能只交付精选。

`stop_kind` 区分策略限制、请求故障、依据不足。故障时 `stopping_allowed=true` 表示允许停止继续收费；`legal_stop=false` 表示尚无完成本轮检索策略的证明，不表示应该自动重试。请求或金额上限、实际不足的补搜核验预留、可证明的三轮范围，均可作为策略停止依据，但不自动满足数量目标或消除待核验条目。

新运行记录每批实际搜索预留键，以及补搜决策使用的关键词、已用/剩余额度和判断指纹。三轮完成证明还要求全部对应请求及响应存在、首批覆盖初始词、没有重复请求键。预留后未发送、接口失败或缺响应，不能计为完成一轮。历史记录缺少轮次凭据时保留未知，不补造执行记录。候选核验上限仍沿用每次 verify 调用的上限，不改为累计限制；被挡住的候选仍属未完成。

相关性理由存在且输入指纹有效，只证明记录可追溯，不证明语义判断正确。维护复盘须对照用户主题、受众、明确排除条件抽审具体例子；不得把人工复盘意见回填成自动流程已经成功的证据。

## 数量例外

2026-10-10 同意先交付 14 条的是当时那一次验收，不是今后的默认目标，也不等于标准 20–30 条数量验收通过。后续新研究仍默认 20。

单独的 `delivery_target_count=14` 不足以批准例外。新例外需要维护者依据明确授权保存 `delivery-target-approval.json`，包含 schema、本轮 UUID、全部资格条件摘要、数量和授权出处；模型不能创建这个文件，公共 API 不提供目标修改入口。复制到另一轮、资格条件变化或只有旧任务的主题/时间摘要时，例外不会生效。缓存重建保留原 UUID，旧任务不被隐式赋予可承接例外的新身份。本次不改任何生产审批记录。

## 缓存接续

取数缺口与写作失败分别处理。原缓存重建后没有任何数值合格候选，且仍缺数据时，在规划/预留模型费用前停止，保留原稿与账本，显示“资料不足”，不再邀请用户反复改空稿。这个分支不能自动提高预算、查询缺失作者页或放宽筛选标准。

已有数值可用案例、但旧完成稿未通过重新核对时，用户可以显式接续；所有权检查和原费用账本仍保留。接口仅返回当前用户的结果。证据正文变化会使只读结果缓存失效；缓存容量覆盖单次历史页的 100 项窗口。

非 200 数据接口错误只补充 HTTP 状态、可用的上游数字码和请求关联 ID，过滤已知 Key；不保存响应正文、自由错误文本或请求头，也不自动重试。这不能找回此前已经丢失的错误详情。

## 验证入口及限制

定向反例在 `tests/test_completion.py`、`tests/test_failure_diagnostics.py`、`webapp/tests/test_cached_analysis.py`、`webapp/tests/test_job_outcome.py` 和 `webapp/tests/test_web.py`。本地真实页面反例运行 `python3 tests/browser_completion.py`，全部使用合成数据。网站类型检查使用既有 `webapp/tsconfig.json`，本地向导使用根目录 `tsconfig.json`。

本地验证不能宣称线上已修复。生产入口另核对实际运行提交，发布后再验收。`scripts/check_versions.py --server <SSH主机别名>` 只读比较工作目录、GitHub main、服务器发布目录及实际进程目录，不拉取、不推送、不部署；仅在发布完成后的版本一致性检查中使用 `--require-synchronized`。开发分支与线上不同是正常状态。

真实研究缓存、逐 ID 复盘、模型响应和截图放在忽略的维护记录目录，不进入 GitHub。完整 CI 与实际生产验收需绑定最终发布提交；定向单元测试不替代它们。

## 网站自动检查与发布

PR 和 main 更新均运行核心检查、下载版浏览器检查，以及独立的网站任务。网站任务包含账号/任务/账本单元测试、严格类型检查、注册到免费报告的完整浏览器流程和完成判定反例。浏览器数据保存在临时目录，未配置真实服务商凭证；只有合成示例和模拟响应。

`ACCEPTANCE_SHA` 指定实际被测提交：PR 使用分支 head，其他事件使用事件提交。代码检出、公开下载安装和验收记录使用同一 SHA，下载版还检查安装标记中的 ref。合并后的发布提交须通过 main 的检查再部署，不能把分支或临时合并提交的绿灯直接当成线上版本证据。

本地运行 `python3 tests/browser_web.py run` 可在临时目录和随机端口完成网站完整流程，结束或失败时清理自己启动的服务。线上验收按用户明确授权的次数执行；免费示例不触发真实数据或模型查询。
