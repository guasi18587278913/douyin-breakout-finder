# 已确认的需求与约束

整理日期：2026-10-09。本文件记录本轮用户确认的方向；实施状态看 testing.md，不把讨论方案当作已经通过验收。

1. 产品交付有依据的选题解读，帮助用户找到值得参考的小号内容，并知道能借鉴什么。
2. 以具体方法串起作品案例，再给迁移示例与行动建议。
3. 保留已认可样稿的自然中文口语、完整解释和具体例子，不压成抽象结论清单。
4. 使用个人报告场景，不写“同学们、下午好、今天我们就聊、我帮你筛了一轮”。
5. 开场直接说当轮发现；示例中的两条、Skill、4000粉丝、30万播放必须随真实结果变化。
6. 作品图卡包含原封面、标题、发布时间、作者、粉丝、原视频链接、主页链接与播放对比。
7. 重点突出本条作品播放量，并展示账号正常播放量与相对倍数。
8. 面向用户统一叫“账号正常播放量”，计算方法保留在详情；底层统计口径不因改名而改变。
9. 图卡放在对应讲述之后，尽量不打断阅读。
10. 统计、日期、链接来自原始记录与程序计算，不让模型提交覆盖字段或补造数字。
11. 标题与简介只能支撑相应观察；未读取正文时不编造真实口播、镜头或叙事结构。
12. 完成判定要对应本版选题解读；不能因不需要的正文步骤一直挂起，也不能把中断或空壳报告标成成功。
13. 只展示已充分核验的合格作品；未核验、有限样本和内部诊断留在本地记录，不能为凑数放宽筛选规则。
14. 明确当前阶段、是否停止与结果位置；七分钟体验需要优化，具体耗时承诺需实测后确定。
15. 标准、样稿、模板、校验随仓库提供，后台实际读取，不依赖本次聊天。
16. 用户把 GitHub 仓库链接交给自己电脑上的 Agent 获取并启动，不做独立安装包流程。
17. 本轮先本地实现并由用户验收，不推送 GitHub、不发版；复用已有数据，不擅自追加付费查询。
18. 不改付费上限、密钥保存方式和分析账户选择；保持用户已经确认的界面精简和署名位置。
19. 跨电脑稳定是结构、口径、证据与展示稳定，不承诺模型逐字相同或每次搜索得到相同作品；模拟与实机验收分开报告。
20. 跨模块改动安排独立审查，修复阻塞问题后再验收。
21. 用户已授权扩大搜索覆盖与候选核验数量，继续遵守原50次请求、0.50美元上限和原筛选标准。先核验已有小号，正文精选数不等于结果池上限。
